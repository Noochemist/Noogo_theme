# 项目规则

## 命令执行提示音（必须遵守）

当需要用户批准敏感命令（即 `requires_approval = true`）时，必须在执行该命令**之前**，先播放系统提示音提醒用户。

1. **强制（机制保证必响）**：所有 `requires_approval = true` 的命令，必须统一写成：

   ```bash
   say 'hello' && <真正需要确认的操作>
   ```
   - 提示音作为命令前缀与敏感操作**合一**，一旦用户批准执行，声音**必然先于操作响起**，无法因"忘记单独放一条"而漏放。
   - 检查点：推送确认命令前，确认其命令文本**以 `say 'hello' &&` 开头**；若缺失，补上前缀再推送。
   - 参数：`blocking = true`（确保声音完整播放后再继续）；如非阻塞，请将 `wait_ms_before_async` 设为 ≥1500ms。
   - 参数：`requires_approval = true`（敏感命令本身仍需用户确认；此时无需再对其作额外处理）。

2. **增强（可选·提前提醒）**：在顺序生成中，若能在推送敏感命令前**单独**再放一条提示音作提前提醒（让声音先于弹窗响起），体验更佳：

   ```bash
   say 'hello'
   ```
   - 参数：`blocking = true`；参数：`requires_approval = false`（不要让自己也要被确认，否则陷入"先确认提示音"的无效流程）。

## 任务难度分级与超时管理（必须遵守）

**开始执行任何任务前，先判断难度并预估时间，将任务归入 A–E 五个等级。** 估时标准：

| 等级 | 预估时间 |
|------|----------|
| A    | 2 分钟   |
| B    | 5 分钟   |
| C    | 10 分钟  |
| D    | 30 分钟  |
| E    | 1 小时（60 分钟） |

1. **启动前**：在首次响应中声明任务等级与预估时间（如「本任务为 B 级，预计 5 分钟」），并说明依据。

2. **硬上限**：任何任务不得超过 **1 小时（E 级上限）**；预估超过 1 小时必须先拆分为多个可独立完成的小任务，逐个交付。

3. **20 分钟提醒**：任务执行到约 **第 20 分钟** 时，主动询问用户是否继续执行。

4. **下载任务与命令行任务（5 分钟规则）**：
   - 下载类任务（如拉取图标/文件/依赖）与命令行任务执行时间**不能超过 5 分钟**。
   - 一旦超过 5 分钟未完成，**必须更换方案**（如更换下载源、改用其他实现方式），不得继续死等。
   - 更换方案后再执行**仍超过 5 分钟**，则立即提醒用户是否**终止该任务**，等待用户决定。

5. **等级升格**：若任务实际推进中难度超出预估（下载超时、技术受阻等），及时向用户报告并重新分级。

## 主题构建与环境（HugMedia）

- `exampleSite/themes/` 下放置了**符号链接**（`themes/HugMedia` → `../../../HugMedia`）指向主题源码，并在 `exampleSite/hugo.toml` 中以 `theme = 'HugMedia'` 指定。
- 因此在 `exampleSite/` 目录下构建（`hugo`）或运行本地服务（`hugo server`）时，**不必指定 `-t`/`--theme` 参数**，也无需任何其他主题配置。

## 编码前必读文档

在开始编码/修改 HugMedia 项目代码前，先读取 `./prompt/` 目录下的以下文件：

1. `scheming/research.implement.md` — 本项目的调研与实施情况记录（设计如何落地、与设计的差异、各阶段进度）。
2. `hugo_coding_conventions.md` — 本项目的编码规范（布局/模板/CSS/JS/图标/多语言等约定）。

## 工作方式（必须遵守）

1. **不实测、不依赖运行时**：用户使用的是旧机器，不要使用无头浏览器，不要实测运行效果，单纯依靠分析代码的方式定位与解决问题。
2. **分析优先、少跑命令**：所有情况下都优先靠代码分析解决；命令行测试能不做就不做，尽量减少命令执行。
3. **敢于质疑用户**：用户也可能犯错，并且常常犯错。当用户的判断失误时，不要一味执行、将错就错地修改；要勇敢提出质疑、解释原因，引导用户意识到问题所在。
4. **新功能先搜索开源方案、不重复造轮子**：在实现新功能、新 Feature、新代码时，先判断这一项新增内容是否是典型的模块化功能。如果是，首先搜索开源解决方案，列出优秀的解决方案供用户参考判断，而不是每次都重复造轮子。
